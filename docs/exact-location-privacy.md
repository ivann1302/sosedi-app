# Точная геолокация: privacy-контракт

Статус: MVP baseline, 07.09.2026. Он описывает два разрешённых сценария и не
разрешает фоновое отслеживание.

## Цели

1. **Поиск рядом.** Однократно получить текущую позицию после выбора радиуса и
   найти доступные вещи через PostGIS.
2. **Точка передачи своего объявления.** По явной команде центрировать picker,
   затем дать владельцу самому подтвердить точку перед публикацией.

Геолокацию нельзя использовать для рекламы, аналитических профилей, фонового
tracking, мониторинга перемещений или добавлять в push, GlitchTip и обычные
логи. Ручной выбор района и ручное касание карты остаются полноценным fallback.

## Минимизация и потоки данных

| Сценарий | Что обрабатывается | Куда передаётся | Хранение |
| --- | --- | --- | --- |
| Поиск рядом | одна пара координат с `LocationAccuracy.low` и радиусом до 50 км | по TLS в `GET /api/v1/items` для `ST_DWithin`/distance | только память catalog provider; не записывается в PostgreSQL, Redis, analytics или mobile storage; очищается при ручном районе/снятии радиуса и завершении процесса |
| Точка объявления | выбранная пользователем пара координат, район и приватный адрес | по TLS в create/edit Item после отдельного подтверждения формы | PostgreSQL в РФ, пока объявление активно и до 30 дней после удаления/закрытия, если данные не нужны действующему обязательству; правила — `data-retention-and-export.md` |
| Yandex Tiles | `x/y/z`, язык, слой, API-ключ, технические сетевые данные | напрямую в Tiles API Яндекса только при видимой карте | приложение не сохраняет тайлы на диск; tile-координаты раскрывают провайдеру область просмотра |

Public Item/Catalog не возвращает точный адрес или координаты. Он использует
стабильную coarse-точку и район. Точные pickup/contact данные доступны только
участникам подтверждённого бронирования и очищаются по общей retention matrix.

[Условия Яндекс Карт](https://yandex.ru/legal/maps_api/ru/) допускают сбор
Яндексом IP, идентификатора устройства и геолокационной информации. Поэтому
нельзя утверждать, что показ карты не создаёт внешний data flow, даже если URL
тайла не содержит исходные `latitude/longitude`. В Tiles-запросы нельзя
добавлять телефон, user/item/booking ID, адрес, поисковый текст или JWT.

## Согласие и отказ

- OS-разрешение запрашивается только после явного действия пользователя и
  только `while in use`; приложение не запрашивает background location.
- До системного диалога экран объясняет конкретную цель. Для поиска: «Получим
  геопозицию один раз, чтобы показать вещи в выбранном радиусе». Для объявления:
  «Получим геопозицию один раз, чтобы поставить точку передачи; перед
  публикацией её можно изменить».
- При отказе, approximate-only разрешении, timeout или отключённой геолокации
  пользователь продолжает работу через район и ручной выбор точки. Повторный
  запрос не показывается автоматически.
- OS-разрешение не заменяет правовое основание для передачи технических данных
  Яндексу. До production-key опубликованная versioned privacy/consent страница
  должна назвать Яндекс, категории данных, цель, условия/политику провайдера и
  способ отозвать разрешение.
- Отзыв разрешения прекращает новые location-вызовы. Сохранённая пользователем
  точка объявления удаляется или изменяется через edit/delete и затем по общей
  retention policy; отзыв не разрушает обязательства активной аренды или спора.

## Проверка перед public release

1. Privacy page и текст согласия одобрены legal/privacy и опубликованы по
   versioned URL.
2. Поиск и picker используют разные понятные pre-permission тексты.
3. Device smoke покрывает allow, approximate, deny, deny-forever и выключенную
   геолокацию; fallback не блокирует основной сценарий.
4. Backend/proxy не сохраняют query string с координатами; GlitchTip и analytics
   redaction test подтверждает отсутствие координат.
5. Фактический Tiles traffic соответствует `yandex-tiles-capacity-and-budget.md`,
   а карта и раздел документов выполняют условия провайдера.
