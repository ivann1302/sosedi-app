# Support contract

## Обычное обращение

`POST /api/v1/support/tickets` создаёт только `GENERAL` ticket. Оно доступно
активному пользователю независимо от наличия, состояния или завершения
бронирований и платежей, поэтому вопрос можно задать и после
`Booking.COMPLETED`/payout.

Обычное обращение:

- не открывает финансовый dispute;
- не блокирует и не создаёт payout;
- не меняет Booking/Payment;
- не обещает и не запускает автоматический refund.

### Ручной процесс проблемы с арендой

Участник может связать `GENERAL` ticket с Booking и одной структурированной
причиной: неявка владельца/арендатора, неисправность при передаче, досрочный или
поздний возврат, повреждение либо утрата. Backend проверяет участника, его роль,
состояние Booking и московскую календарную дату; mobile показывает только
допустимые причины. Создание такого обращения не меняет Booking, Payment или
сумму и не создаёт финансового обещания. Поддержка ведёт обычный private thread;
денежное решение появится только в отдельном утверждённом dispute flow.

## Финансовый dispute

Financial dispute — отдельная actor/state machine, связанная с конкретной
Booking и утверждённым payment scenario. Её окно, решения и денежные последствия
остаются `BLOCKED` до принятия ADR из раздела 13.1 `MVP_CHECKLIST.md`.
`SupportTicket.type = DISPUTE` пока не доступен через пользовательский или
operator Support API. Все list/thread/upload запросы Support API явно фильтруют
`GENERAL`; даже собственная связанная с Booking запись `DISPUTE` там не
раскрывается и получает нераскрывающий `404`.

## Thread и вложения

Исходное сообщение хранится в ticket, последующие сообщения — append-only в
`support_messages`. Пользователь видит только собственный `GENERAL` ticket;
operator использует MFA admin-session с capability `SUPPORT`. Закрытый ticket не
принимает новые сообщения.

Оператор может атомарно закрыть только свободное обращение либо обращение,
назначенное ему самому. Закрытие требует CSRF, записывает PII-free
`SUPPORT_TICKET_CLOSED` audit с переходом статуса и создаёт transactional outbox
событие для in-app inbox пользователя. Повторное закрытие и попытка закрыть
обращение другого оператора получают `409`.

Изображения загружаются в private bucket через actor/ticket-bound
`SUPPORT_ATTACHMENT` intent. При создании сообщения backend повторно проверяет
bucket/key/MIME/размер/magic bytes, безопасно декодирует и повторно кодирует
изображение без metadata/вредоносного хвоста, вычисляет SHA-256 очищенных байтов и
атомарно потребляет intent.
API возвращает только metadata/hash; скачивание выполняется по отдельной
60-секундной presigned URL после повторной object-level проверки.
